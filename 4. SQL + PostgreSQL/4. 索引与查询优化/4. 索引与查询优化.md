# 4. 索引与查询优化

> 配套可运行脚本：`4. 索引与查询优化.py`

## 0. 一句话结论

**没有索引，数据库要「全表扫描」一行行查；有索引能快速定位。但「有索引 = 一定快」是错误理解——真正的依据是执行计划（`EXPLAIN`）。**

---

## 1. 全表扫描 vs 索引

查询：

```sql
SELECT *
FROM users
WHERE username = 'Tom';
```

**没有索引**：数据库可能需要：

```text
user1 -> user2 -> user3 -> ... -> user10000000  一个个检查
```

这就是 **Full Table Scan（全表扫描）**。

**建索引**：

```sql
CREATE INDEX idx_users_username
ON users(username);
```

数据库利用索引快速定位，就像查字典的目录。

---

## 2. 查询是怎么被执行的

```text
SQL
  ↓
Query Planner（查询规划器）
  ↓
选择执行计划
  ↓
Index Scan / Seq Scan / ...
  ↓
执行
```

数据库不是「按你写的顺序」执行，而是**规划器选择最优计划**。所以要看执行计划，而不是猜。

---

## 3. EXPLAIN / EXPLAIN ANALYZE

PostgreSQL：

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE username = 'Tom';
```

输出会告诉你：

- 用的是 `Index Scan` 还是 `Seq Scan`（顺序扫描）
- 扫描了多少行、花了多少时间

> sqlite 对应命令是 `EXPLAIN QUERY PLAN`（脚本里演示了）；PostgreSQL 用 `EXPLAIN ANALYZE`。

**这是从「会写 SQL」进入「会优化 SQL」的关键一步。**

---

## 4. 索引不是万能的

| 情况 | 说明 |
|------|------|
| 小表 | 全表扫描可能更快（索引本身有开销） |
| 低区分度列 | 如性别「男/女」，建索引收益小 |
| 写多读少 | 每次 INSERT/UPDATE/DELETE 都要维护索引 |
| 索引占空间 | 额外存储和内存开销 |

> 原则：**先看执行计划，再决定建不建索引，而不是拍脑袋。**

## 6. 小结

| 概念 | 一句话 |
|------|--------|
| 全表扫描 | 无索引，一行行查 |
| 索引 | 快速定位的「目录」 |
| 查询规划器 | 自动选最优执行计划 |
| EXPLAIN | 看执行计划，优化 SQL 的依据 |

**核心认知**：索引是「用空间换时间」——读变快，写变慢、占空间。优化慢查询的正确姿势是：先 `EXPLAIN ANALYZE`，看它到底在哪儿慢，再对症下药。
