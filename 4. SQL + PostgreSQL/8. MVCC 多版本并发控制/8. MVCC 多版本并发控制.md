# 8. MVCC 多版本并发控制

> 配套可运行脚本：`8. MVCC 多版本并发控制.py`

## 0. 一句话结论

**MVCC（Multi-Version Concurrency Control）是 PostgreSQL 的并发核心——写不覆盖旧数据，而是产生新版本；每个事务看到自己的「快照」，所以读不阻塞写、写不阻塞读。**

---

## 1. 核心思想

PostgreSQL 为了让多个事务更好地并发工作，不是简单地「一个事务把数据库锁死」，而是：

```text
事务 A -> 看到某个版本的数据（快照）
事务 B -> 修改产生新的数据版本（不覆盖旧的）
事务 A -> 根据事务可见性规则，决定自己应该看到哪个版本
```

---

## 2. 一行数据 = 多个版本

MVCC 下，`UPDATE` 不是覆盖，而是**追加新版本**：

```text
balance 这一行的版本链：
  版本 1（初始）      -> 100
  版本 2（事务B提交） -> 80
  版本 3（事务C提交） -> 120
```

旧版本不立刻删除，等没有事务再需要它们时才被清理（**VACUUM**）。

---

## 3. 快照隔离

事务开始时，数据库给它一个「快照」：

```text
事务A 开始 -> 快照 balance=100
事务B 修改 balance=80 并提交
事务A 再读 -> 仍看到 balance=100（自己的快照）
```

事务 A 看到的是「它开始那一刻」的数据，不受并发修改干扰。

---

## 4. 好处与代价

| 好处 | 代价 |
|------|------|
| 读不阻塞写、写不阻塞读 | 旧版本占空间，需 VACUUM 清理 |
| 事务看到一致快照 | 长事务可能拖慢清理 |
| 高并发性能好 | 理解成本更高 |

---

## 5. 与锁的关系

| | 锁（第 7 节） | MVCC（本节） |
|--|--------------|--------------|
| 思路 | 悲观：先锁再操作 | 乐观：多版本 + 快照 |
| 阻塞 | 写可能阻塞读 | 读写不互阻塞 |
| 用途 | 显式锁定（FOR UPDATE） | PostgreSQL 默认隔离机制 |

两者**配合**实现事务隔离（ACID 的 I）。

## 7. 小结

| 概念 | 一句话 |
|------|--------|
| MVCC | 多版本并发控制 |
| 快照 | 每个事务看自己的版本 |
| VACUUM | 清理不再需要的旧版本 |
| 价值 | 读写不互阻塞，并发性能好 |

**核心认知**：MVCC 是 PostgreSQL 区别于「锁死一切」的优雅方案——用「多版本 + 快照」换高并发。以后学 FastAPI + PostgreSQL 并发问题时，这是地基。
