# 5. 数据库表设计与约束

> 配套可运行脚本：`5. 数据库表设计与约束.py`

## 0. 一句话结论

**后端开发不能只会查询，还要会「设计表」。约束（PRIMARY KEY / NOT NULL / UNIQUE / CHECK / DEFAULT / FOREIGN KEY）在数据库层兜底数据正确性，关系（一对一/一对多/多对多）是后端系统的数据基础。**

---

## 1. 建表与约束

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,            -- 自增主键
    username VARCHAR(50) NOT NULL UNIQUE, -- 非空 + 唯一
    age INTEGER CHECK (age >= 0),         -- 校验约束
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP  -- 默认值
);
```

| 约束 | 作用 |
|------|------|
| `PRIMARY KEY` | 唯一标识一行，不能空、不能重 |
| `NOT NULL` | 不允许空值 |
| `UNIQUE` | 值唯一，不能重复 |
| `CHECK` | 值必须满足条件 |
| `DEFAULT` | 缺省时用默认值 |
| `FOREIGN KEY` | 引用另一张表的主键 |

> PostgreSQL 自增主键用 `BIGSERIAL`；sqlite 用 `INTEGER PRIMARY KEY`。

---

## 2. 约束 = 数据库层的兜底

约束让「脏数据根本进不来」：

```text
username 为 NULL      -> NOT NULL 违反，报错
username 重复         -> UNIQUE 违反，报错
age = -5             -> CHECK 违反，报错
外键指向不存在的主键  -> FOREIGN KEY 违反，报错
```

即使应用代码有 bug，数据库也能挡住非法数据——这是最后一道防线。

---

## 3. 三种关系

### 一对多（最常见）

```text
User
  ├── Order
  ├── Order
  └── Order
```

```sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),  -- 外键
    amount NUMERIC
);
```

### 多对多（需要中间表）

```text
users  ←→  user_groups（中间表）  ←→  groups
```

```sql
CREATE TABLE user_groups (
    user_id  INTEGER REFERENCES users(id),
    group_id INTEGER REFERENCES groups(id)
);
```

### 一对一

两张表各一行对应，较少用（通常可合并进一张表）。

## 5. 小结

| 概念 | 一句话 |
|------|--------|
| 约束 | 数据库层的数据校验 |
| 一对多 | 主键 → 外键 |
| 多对多 | 中间表 |
| 意义 | 后端系统的数据基础 |

**核心认知**：表设计决定数据「怎么存、怎么关联、怎么保证正确」。ORM 只是把表映射成对象——真正的设计能力在 SQL 层。先把表和约束设计对，再谈 ORM。
