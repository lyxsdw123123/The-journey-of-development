# 7. 锁与死锁

> 配套可运行脚本：`7. 锁与死锁.py`（用 Python 线程锁模拟死锁）

## 0. 一句话结论

**并发事务会竞争同一份数据，锁用来协调访问。PostgreSQL 最常用 `SELECT ... FOR UPDATE` 加行级排他锁；死锁是互相等待，数据库会自动回滚一方来解除。**

---

## 1. 事务 → 并发 → 锁

```text
事务
  ↓
并发（多个事务同时跑）
  ↓
锁（协调谁先谁后）
```

两个事务同时给同一行扣款，可能读到同一份余额，导致「丢失更新」。锁保证同一时刻只有一个事务能改某一行。

---

## 2. FOR UPDATE：行级排他锁

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

- 给查出来的这一行加**排他锁**。
- 别的事务要改这行就得**等**。
- 是「先读后改」场景防止并发冲突的标准做法。

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 锁住这一行
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;   -- 提交时释放锁
```

---

## 3. 共享锁 vs 排他锁

| 锁 | 含义 | SQL |
|----|------|-----|
| 共享锁 | 多人可同时读，但不能写 | `FOR SHARE` |
| 排他锁 | 独占，别人不能读也不能写 | `FOR UPDATE` |

类比：

- 共享锁 = 图书馆的书：多人同时看，但没人能撕。
- 排他锁 = 你正在改的文档：别人既不能看也不能改。

---

## 4. 行锁 vs 表锁

| 锁 | 粒度 | 并发度 |
|----|------|--------|
| 行锁 | 只锁相关几行 | 高（PostgreSQL 默认） |
| 表锁 | 锁整张表 | 低 |

```sql
-- 行锁
SELECT ... FOR UPDATE;

-- 表锁
LOCK TABLE accounts IN EXCLUSIVE MODE;
```

---

## 5. 死锁

```text
事务1：先锁 A 行，再想锁 B 行
事务2：先锁 B 行，再想锁 A 行

事务1 等 B，事务2 等 A -> 互相等待 -> 死锁
```

```text
事务1 ──锁──> A          B <──锁── 事务2
        │                │
        └──── 互等对方 ────┘
```

**数据库的做法**：检测到死锁后，自动**回滚其中一个事务**来打破僵局（脚本里用 Python 线程锁模拟了「互相等待」）。

> 工程上避免死锁：让所有事务**按相同顺序**访问资源（都先 A 后 B），就能大大降低死锁概率。

## 7. 小结

| 概念 | 一句话 |
|------|--------|
| 锁 | 协调并发访问 |
| FOR UPDATE | 行级排他锁 |
| 共享/排他 | 多人读 / 独占写 |
| 死锁 | 互相等待，数据库自动回滚一方 |

**核心认知**：锁是「悲观并发控制」——先锁住，再操作。下一节的 MVCC 是 PostgreSQL 的「乐观」方案，两者配合实现事务隔离。
