# Dev Learning Notes（开发学习笔记组织规范）

把「学习一个知识点」沉淀成**可读、可验证、可增量扩展**的笔记仓库，而不是一次性问答。

## 何时使用

当用户表达想「系统学习某个开发主题」，且产出要被长期积累（建目录、写文件、进 git）时，按本规范组织文件。典型场景：

- 「学习 Python 解释器执行流程」
- 「讲一下协程 / 内存模型 / 垃圾回收是怎么工作的」
- 「帮我整理一份 X 知识点的笔记」

## 目录结构约定

每个「主题」是一个顶层文件夹，主题下按「序号. 知识点」拆分子文件夹：

```text
<主题名称>/
├── 1. <知识点A>/
│   ├── 1. <知识点A>.md    # 讲解文档（必填）
│   └── ...                 # 参考文件（按主题类型，可选）
├── 2. <知识点B>/
│   └── 2. <知识点B>.md    # 也可以只有 .md
└── README.md              # 可选：主题内目录说明
```

规则：

1. 序号用 `1.`、`2.`、`3.` 前缀（数字 + 英文点 + 空格），保证文件系统按顺序排列。
2. 每个知识点**至少**一份 `.md` 讲解文档（核心，必填）。
3. 参考文件**按主题类型选择，不强制 `.py`**：
   - Python 知识点 → `.py`（可运行演示）
   - SQL / 数据库 → `.sql`
   - Docker → `Dockerfile`、`compose.yaml`
   - 配置 / 部署 → `.yaml`、`.env`、`.conf`
   - 概念性 / 综述性 / 无合适文件类型 → 只保留 `.md`
4. 后续新增知识点只追加新序号文件夹，**绝不重排已有序号**（保持链接/引用稳定）。

## 参考文件规范（若提供）

- 参考文件要「能跑 / 能用」：`.py` 能运行、`.sql` 能执行、`compose.yaml` 能 `docker compose up`。
- Python 的 `.py`：
  - 顶层 docstring 先写「一句话结论 + 流程图」。
  - 用章节函数分段（如 `section(title)` 打印分隔线），按「源码 → 原理逐层 → 实验 → 小结」推进。
  - 优先用标准库自证（讲解释器用 `tokenize` / `ast` / `dis`，讲性能用 `timeit`）。
  - Windows 控制台中文乱码时，加 `sys.stdout.reconfigure(encoding="utf-8")`。
  - **写完必须实际运行一遍**，以「无报错、输出完整」为完成标准。
- 非 Python 的参考文件（`.sql` / `Dockerfile` / `compose.yaml` 等）：
  - 直接给出**完整、可复制**的真实文件内容，而不是只把内容贴在 `.md` 或 `.py` 里。
  - 若本机无对应运行环境（如未装 Docker / PostgreSQL），在 `.md` 里说明「需 X 环境」。

## .md 讲解文档规范

结构建议：

1. 开头一句话结论。
2. 完整流程 / 原理（配表格或图）。
3. 逐层拆解（对应参考文件 / 示例）。
4. 动手清单（可复制的命令 / 代码片段）。
5. 小结表格（层次 / 关键词 / 工具 / 记住什么）。

## 收尾必做

- 验证参考文件可用：`.py` 跑通；`.sql` / `compose.yaml` 语法正确（无环境时至少在 `.md` 标注）。
- 在仓库或主题级 README 的「知识点索引」里登记本次新增内容，保持目录可索引。
- 提交 git 时，commit message 写清「新增：<主题>/<知识点>」。

## 示例

- Python 知识点：`1. Python运行机制/1. Python解释器执行流程/`（.py + .md）
- Docker 知识点：`7. Docker/5. Dockerfile 详解/`（Dockerfile + .md）
- 仅 .md 也 OK：概念性、综述性的知识点，可只写一份 .md
