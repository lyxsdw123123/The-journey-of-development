# 7. Python 工程开发必须形成的思维

> 配套可运行脚本：`7. Python工程开发必须形成的思维.py`

## 0. 一句话结论

**从「脚本思维」升级到「工程思维」：关注对象的生命周期、用 `with` 管理资源、用分层结构设计模块——从「能跑就行」到「健壮、可维护、可复用」。**

---

## 1. 脚本思维 vs 工程思维

| | 脚本思维 | 工程思维 |
|--|----------|----------|
| 关注点 | 能跑出结果就行 | 健壮、可维护、可复用 |
| 资源 | `open()` 后可能忘了关 | `with` 保证释放 |
| 结构 | 一个 `main.py` 塞满 | 分层目录、单向依赖 |
| 生命周期 | 不关心对象何时创建/销毁 | 主动设计对象的生与死 |

---

## 2. 生命周期：对象何时创建、何时销毁

以 Web 框架（FastAPI）为例：

```python
@app.get("/")
def hello():
    data = []      # 每次请求：创建 list
    ...            # 使用
    return data    # 请求结束：引用归零 -> 自动释放
```

**每个对象的生命周期：**

```text
创建  ->  使用  ->  释放
（请求开始）（处理中）（引用计数归零）
```

三类对象的典型生命周期：

| 对象 | 生命周期 | 注意 |
|------|----------|------|
| 函数内局部变量 | 函数返回即销毁 | 最安全，天然短暂 |
| 模块级变量 | 进程存活期间一直存在 | 慎用，容易变全局状态 |
| 缓存/连接池 | 跨请求复用 | 要主动管理创建与销毁 |

> 工程思维 = 写每一行代码时，都知道这个对象「何时生、何时死、谁来负责释放」。

## 3. 资源管理：`with` 上下文管理器

**错误写法**（脚本思维）：

```python
file = open("a.txt")
data = file.read()
# 问题：如果 read 抛异常，下面的 close 不会执行 -> 文件泄漏
```

**正确写法**（工程思维）：

```python
with open("a.txt") as f:
    data = f.read()
# with 块结束（无论是否异常），f.close() 一定被调用
```

`with` 的本质是「上下文管理器」，适用于一切需要「进入/退出配对」的资源：

- 文件：`with open(...)`
- 锁：`with threading.Lock():`
- 数据库连接、网络连接
- 自定义的计时、日志、事务

自定义上下文管理器：

```python
class Timer:
    def __enter__(self):
        self.t0 = time.perf_counter()
        return self
    def __exit__(self, exc_type, exc, tb):
        print(f"耗时 {time.perf_counter() - self.t0:.4f}s")

with Timer():
    do_work()
```

> **心法**：凡是「拿到后必须归还」的东西，都用 `with` 包裹，让释放「异常也安全」。

## 4. 模块设计：从 `main.py` 到分层目录

**脚本思维**：

```text
main.py   （所有逻辑塞一起，越写越长）
```

**工程思维**：

```text
project/
├── app/            # 应用入口、路由、配置
│   ├── __init__.py
│   └── main.py
├── services/       # 业务逻辑层
│   ├── __init__.py
│   └── user_service.py
├── models/         # 数据模型层
│   ├── __init__.py
│   └── user.py
├── utils/          # 通用工具
│   ├── __init__.py
│   └── helpers.py
├── tests/          # 测试
│   └── test_user.py
└── main.py         # 顶层入口，只负责启动
```

设计原则：

1. **每层只做一件事**：`app` 管路由，`services` 管业务，`models` 管数据，`utils` 管工具。
2. **依赖单向**：`app -> services -> models`，绝不反向 `import`（避免循环依赖）。
3. **测试分离**：`tests/` 与源码分开，能持续验证。
4. **`__init__.py`**：让每个目录成为可 `import` 的包。

---

## 5. 三条工程思维的落地清单

1. **生命周期**
   - 问自己：这个对象在哪创建？谁持有？何时释放？
   - 尽量用局部变量，少用全局/模块级状态。

2. **资源管理**
   - 文件、连接、锁，一律 `with`。
   - 有「进入/退出」成对逻辑的，抽成上下文管理器。

3. **模块设计**
   - 单一职责，分层组织。
   - 依赖单向，可测试。

## 7. 小结

| 思维 | 关键动作 |
|------|----------|
| 生命周期 | 明确对象创建/销毁时机 |
| 资源管理 | 一律 `with`，异常也释放 |
| 模块设计 | 分层、单向依赖、可测试 |

**核心转变**：从「能跑就行」到「健壮、可维护、可复用」——这就是工程思维。
